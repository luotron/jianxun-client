# Flutter AppVest 单连接收发复现

日期：2026-10-19。场景：Flutter AOT 应用已有 HTTP 登录实现，仅缺 TCP 消息收发。
目标：恢复网关传输，复用同一个 socket 发送、接收并保持心跳。
本记录省略目标域名、账号、凭据与业务群标识。

执行链：读取项目与抓包 → Flutter 插件 Java 层定位 → 原生库 IDA 分析 →
重组网关 TCP 流 → 恢复首包与 XOR → 实现控制通道发现 →
实现 IM 帧与会话加密 → 单连接并发测试 → 原生构造函数字节对照 → 双账号线上验证。

可复用发现：

- 不按端口名称猜协议；对照完整 TCP 流、插件调用链和实际原生库。
- 逻辑目标与网关地址分别保存。域名模式的目标槽可能包含完整 `HOST:PORT`，
  改成解析 IP 会改变调度和目标映射。
- 首包长度与 AES 正确不代表握手完整。启动计数、网络类型、会话 ID 和包名缺失，
  仍可能触发网关 EOF。
- 后台只保留一个 socket 读取者，用 clientSeq 将 ACK 分配给发送等待者，
  推送进入独立消息队列。RECV 与 SENDACK 同包或乱序到达应纳入测试。
- 接收等待超时与连接断开分别处理；回执未知时不要自动重发造成重复业务消息。
- 原生仿真对照需明确哪些依赖由桩实现；最终再以线上认证和真实接收验证。

本地验证入口：

```powershell
python -m unittest discover -s tests -v
python tools/verify_qlck_native.py
```

结果：7 项测试通过，原生首包与 Python 字节相同，群消息接收及私聊双向收发成功。
运行依赖未增加；原生对照工具使用现有 Unicorn 和 pyelftools。
